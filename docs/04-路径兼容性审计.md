# 04 · 路径兼容性审计

> 结论先行：**格式号对 ≠ 游戏里对。** `pack_format` 只决定游戏肯不肯加载这个包；
> 包里的**文件路径**对不对，才决定内容有没有生效。本篇是这件事的核对结果与复现方法。

## 为什么会有"孤儿文件"

资源包是**被动覆盖**：游戏读原版的某个路径，发现有同名文件就用你的，没有就用原版的。
原版一旦在某个小版本改了路径，你放在旧路径下的那份文件就变成**孤儿** ——
**不报错、不崩溃、日志也不提示，只是不生效**。构建、CI、格式号全都正常。

## 实测结果：各线有多少文件不生效

同一份主体（2715 个文件），对照各线目标版本的官方 client jar：

| 线 | MC | 你改过、但该版本原版已不读的文件数 |
| --- | --- | --- |
| `mc1.16` | 1.16.5 | **0**（主体内容的年代，天然对齐） |
| `mc1.17` | 1.17.1 | 8 |
| `mc1.18` | 1.18.2 | 8 |
| `mc1.19` | 1.19.4 | 11 |
| `mc1.20` | 1.20.6 | 14 |
| `mc1.21` | 1.21.11 | 71 |
| `mc26.1` | 26.1.2 | 130 |
| `mc26.2` | 26.2 | 156 |
| `mc26.3` | 26.3 | 156 |

> 这里的数字只统计"**你改过、但该版本原版不读**"的文件，也就是真损失。
> 主体里另有一批只属于较新版本的文件（`sculk_sensor`、`axolotl` 等 217 个），
> 它们在老版本下只是白带、不统计在内 —— 这也是为什么 `mc1.16` 那行是 0 而不是 217。

漂移是**累积**的：原版每改一次路径，就多一批文件在这条线及之后所有线失效。

以 mc26.3 为例，五分类（审计工具的输出）：

| 分类 | 数量 | 含义 |
| --- | --- | --- |
| 原版也有此路径 | 1784 (65.7%) | 正常覆盖，通用 |
| 原版是后来才加的 | 217 (8.0%) | 覆盖较新原版文件，正常 |
| 包自建文件（原版从来没有） | 524 (19.3%) | 自建资源，正常 |
| 与 1.16.5 原版逐字节相同 | 34 (1.3%) | 丢了也不影响外观（只是白带） |
| **你改过、原版已不读此路径** | **156 (5.7%)** | **需要 overlay，否则你的改动在新版本下不生效** |

> 只有最后一类是问题。前四类都是正常的 —— 尤其"包自建文件 524 个"（如 `bee_hive1..5`、
  `daylight_detector_00..15` 这类自己加的变体模型），原版没有它们是理所当然的。

## 已确认的原因（都是原版改路径，不是我们写错）

| 版本 | 从 | 到 | 影响 |
| --- | --- | --- | --- |
| 1.17 | `texts/credits.txt` | `texts/credits.json` | 你自定义的 credits（7411 B，原版 10566 B）**自 mc1.17 起就没显示过** |
| 1.20.2 起 | `textures/gui/…` 部分图标 | `textures/gui/sprites/…` | 空盔甲槽图标等 |
| 1.21.2 | `textures/entity/arrow.png`、`squid.png`、`cow.png`、`pig.png`、`sheep_fur.png`、`alex/steve.png` 等 | 拆进 `entity/projectiles/`、`entity/squid/`、`entity/cow/`、`entity/player/{slim,wide}/` 等子目录 | 实体贴图大面积失效 |
| 1.21.2 | `textures/models/armor/*_layer_*.png` | `textures/entity/equipment/humanoid*/…` | 13 个盔甲贴图 |
| 1.21.2 | `textures/environment/sun.png` | `textures/environment/celestial/sun.png`（`moon_phases.png` 拆成逐月相文件） | 日月贴图 |
| 1.21.4 | `models/item/*.json` | `items/*.json`（新 schema） | 7 个物品模型（见下方"待确认"） |
| 1.21.5+ | `entity/{cow,pig,chicken,cat,rabbit,bed,signs,llama/decor}/*` | 变体化 / 子目录化 | 26.x 下累计 156 个 |

## 怎么自己查一遍

```sh
python tools/audit.py --line mc26.3           # 列出该线“改了但不生效”的文件 + 猜测新路径
python tools/audit.py --list                  # 有哪些线
python tools/audit.py --line mc26.3 --strict  # 有需处理文件时退出码 1（可用于 CI）
python tools/audit.py --all                   # 全部线（会下载多个官方 jar，20-40 MB/个）
python tools/audit.py --line mc26.3 --json    # 机器可读（人读日志走 stderr）
python tools/audit.py --line mc26.3 --no-baseline   # 跳过与基线版本的字节比对
```

工作原理与参数：

- 拿官方 `version_manifest_v2.json` → 该版本 client jar 当参照（下载时校验 sha1），
  列出 `assets/minecraft/**` 的全部条目，把该线最终打包的文件分成上面那五类。
- **`--baseline`（默认取本包最老那条线的目标版本，即 1.16.5）**：用来区分
  "原版把这个路径改名/移除了"和"这是你自己加的文件"。没有基线就无法区分，只能报"该版本原版没有"。
- jar 缓存在 `dist/.jarcache/`（`dist/` 已 gitignore），同一版本只下载一次；
  版本清单也缓存 24 小时，避免每次都打 Mojang。
- **新增/更新一条版本线后都应该跑一次**，这是目前唯一能提前发现"格式号对了但游戏不认"的办法。

## 已知未修 & 处理方式

**修法是给对应线补 overlay，不是改主体** —— 主体要照顾 mc1.16 ~ mc1.20，那些老路径在那儿是对的。
具体流程见 [07-改动与-backport](07-改动与-backport.md)。

> ⚠️ 这些孤儿**不影响构建**：`build.py` 照样通过、格式号也对，CI 全绿。
> 它们只影响游戏内表现，所以只能靠审计发现，不会自己爆出来。

> 📌 **`mc1.21.4+` 的物品模型（`models/item/` → `items/`）目前看可能无害**：原版新的
> `items/waxed_copper_block.json`、`items/infested_stone.json` 指向 `block/copper_block`、
> `block/stone`，恰好等于你当年想达到的效果（蜡铜看着像铜、虫蚀石看着像石头）。
> 但这是**从路径推断的，没有游戏内实测**。

> 📌 审计只能证明"这个路径游戏不读了"，**不能证明"游戏里看起来不对"** ——
> 原版可能恰好采用了你当年的做法（如上一条）。所以补 overlay 之前，
> 能进游戏看一眼最稳。
