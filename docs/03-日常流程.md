# 03 · 日常流程

## 先确认你在哪条分支

```sh
git branch --show-current          # 例：1.16.5
git show HEAD:FPP/pack.mcmeta      # 确认格式号 / 版本号是你以为的那条线
```

**改动前一定先确认分支** —— 这是分支制最容易踩的坑：在错的分支上改东西，提交后才发现
"这条线不需要这个改动"或"该改的线没改到"。

## PR 打到哪条分支

| 你要做的事 | 目标分支 | 开 PR |
| --- | --- | --- |
| 更新**最新** MC 版本的材质（跟着 MC 换代走） | `master` | `gh pr create --base master` |
| 修**老版本**的 bug / 调整 | 那条版本线 | `gh pr create --base 1.16.5` |

**通用改动要在每条还在维护的线上各开一次 PR**。原因见 [01](01-分支模型与纪律.md)：
两条版本线之间不许 merge / rebase。

## 场景一：改一张通用贴图（绝大多数情况）

```sh
git switch -c fix/lantern master       # 1. 从要改的分支开主题分支（别直接改分支本体）
# 2. 改 FPP/assets/minecraft/textures/...
git add FPP/assets/minecraft/textures/block/lantern.png   # 只 add 你动过的（别用 -A）
git commit -m "fix: 灯笼动画"
git push -u origin HEAD                # 3. 推主题分支
gh pr create --base master             # 4. PR 打回那条线；合并后主题分支随手删掉
```

如果这条改动**所有版本线都要**，就逐线同步（`master`、`1.16.5`、`1.15.2`、…），**每条线一个 PR**：

```sh
git format-patch -1 --stdout > /tmp/lantern.patch      # 在改好的那条线上导出
for b in 1.16.5 1.15.2; do
  git switch -c sync/lantern-$b $b                     # 每条线各开一个主题分支
  git apply --index /tmp/lantern.patch                 # --index 才不会漏掉 patch 里新增的文件
  git commit -m "fix: 灯笼动画（同步自 master）"
  git push -u origin HEAD
done
# 然后每条线各开一个 PR，例：
# gh pr create --base 1.16.5 --head sync/lantern-1.16.5 --title "fix: 灯笼动画（同步自 master）"
```

> 版本线（`1.16.5` / `1.15.2`）目前**没有强制 PR 保护**，直接 `git push origin 1.16.5` 也能推上去；
> 但走 PR 才有记录、也不会绕过核验，所以推荐一律走 PR。

**同步清单**（贴到 PR 描述或 issue 里，改完打勾）：

```
同步范围：[ ] master  [ ] 1.16.5  [ ] 1.15.2  [ ] 其它：______
```

> 只改**某些**分支也完全正常 —— 老版本冻结后本来就不该再动。判断标准是"这条线还需要这个改动吗"，
> 而不是"理论上应该一致"。

## 场景二：只有某个版本需要的改动

直接在那条分支上改，不需要同步：

```sh
git switch 1.16.5
git switch -c 1.16.5/fix-credits
# 只在这条线放这个文件（例：1.17+ 才用 texts/credits.json，1.16.5 用 texts/credits.txt）
```

该版本与其它版本路径不同时，照 [06-各版本路径变化对照](06-各版本路径变化对照.md) 查原版读哪个路径。

## 场景三：发一个版本

```sh
git switch 1.16.5
git switch -c release/v8.8-1.16.5
# 1. 改 FPP/pack.mcmeta 的 version 字段 → "v8.8 for MC1.16.5"
# 2. 打包：Windows 上通常没有 zip 命令，用 Python 标准库
python - <<'PY'
import zipfile
from pathlib import Path
root, out = Path("FPP"), Path("FPP_v8.8_for_MC1.16.5.zip")
files = sorted(p for p in root.rglob("*") if p.is_file())
with zipfile.ZipFile(out, "w", zipfile.ZIP_DEFLATED) as z:
    for p in files:
        z.write(p, p.relative_to(root).as_posix())   # 根目录直接是 pack.mcmeta + assets/
print(out, len(files), "个文件")
PY
# 3. PR → 合并 → 打 tag 并发布
git switch 1.16.5 && git pull
git tag v8.8-1.16.5 && git push origin v8.8-1.16.5
gh release create v8.8-1.16.5 FPP_v8.8_for_MC1.16.5.zip \
  --repo TecoStudio/Frozen_Pear_Pack --title "FPP冻梨子材质 v8.8 for MC1.16.5" --notes "..."
```

- tag 与资产命名规范见 [02-分支与命名](02-分支与命名.md)。
- **打 tag 前先核验**（见 [07-核验一条分支](07-核验一条分支.md)）：格式号对不对、路径有没有失效。
- 打包前删掉 `FPP/` 里混进的工作文件（`.DS_Store`、`.pdn`、`*.bak` 之类）。

## 场景四：回滚

```sh
# 只是本地改乱了
git restore FPP/

# 已经提交但还没推送
git reset --soft HEAD~1        # 保留改动，撤掉提交

# 已经推送（在主题分支上）
git revert <commit>            # 用 revert，别在共享分支上 force push

# 已经发布（tag + Release）
# 不要动/重命名已发布的 tag；发一个新版本号修掉，并在 Release notes 里说明
```

## 常见疑问

| 现象 | 说明 |
| --- | --- |
| 推送后仓库首页出现 `1.16.5 had recent pushes → Compare & pull request` | GitHub 对"最近推送过、还没有 PR 的分支"的自动建议，**官方没有关闭开关**（社区请求 [#116576](https://github.com/orgs/community/discussions/116576)、[#35200](https://github.com/orgs/community/discussions/35200) 都还开着）。点横幅上的 Dismiss 只关掉你自己的视图；也可以直接忽略，它过一阵自己消失。每次往这类长期分支推东西都会再冒一次，**不影响分支、保护规则或 Release**。带 `LIPiston:` 前缀的那种，是推送来自 fork 时在父仓库上的写法。 |
| 推送被拒绝：`protected branch hook declined` | 你直接往 `master` 推了。`master` 强制走 PR（管理员也一样）—— 开主题分支再提 PR。 |
| 游戏里显示"不兼容" | `pack_format` 与该 MC 版本不符 —— 见 [05](05-pack.mcmeta-与格式号.md)。 |
| 贴图改了但游戏里没变化 | 多半是路径问题（原版把资源挪了位置）—— 见 [06](06-各版本路径变化对照.md)、[07](07-核验一条分支.md)。 |
| zip 装上去没效果 | 包根目录必须直接是 `pack.mcmeta` + `assets/`，不能再套一层 `FPP/`。 |

## 常用检查

```sh
git branch -r                                  # 有哪些远端分支
git remote -v                                  # origin 是主仓库（TecoStudio）
git show HEAD:FPP/pack.mcmeta                  # 当前分支的格式号 / 版本号
git log --oneline -5                           # 当前分支最近做了什么
git diff --stat 1.16.5..master -- FPP          # 两条线之间差了多少文件
git status --short                             # 工作区是否干净
```
