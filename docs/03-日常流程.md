# 03 · 日常流程

## 先确认你在哪条分支

```sh
git branch --show-current          # 例：mc1.16.5
git show HEAD:FPP/pack.mcmeta      # 确认格式号 / 版本号是你以为的那条线
```

**改动前一定先确认分支** —— 这是分支制最容易踩的坑：在错的分支上改东西，提交后才发现
"这条线不需要这个改动"或"该改的线没改到"。

## 场景一：改一张通用贴图（绝大多数情况）

```sh
git switch -c fix/lantern master       # 1. 从要改的分支开主题分支（别直接改分支本体）
# 2. 改 FPP/assets/minecraft/textures/...
git add FPP/assets/minecraft/textures/block/lantern.png   # 只 add 你动过的（别用 -A）
git commit -m "fix: 灯笼动画"
git push -u origin HEAD                # 3. 开 PR 合并回该分支
```

如果这条改动**所有版本线都要**，就要逐分支同步（`master`、`mc1.16.5`、…）：

```sh
git format-patch -1 --stdout > /tmp/lantern.patch
for b in mc1.16.5 mc1.15.2; do
  git switch $b && git apply --index /tmp/lantern.patch && git commit -m "fix: 灯笼动画（同步自 master）"
done
```

> 用 `git apply --index` 而不是 `git apply` + `git commit -a`：后者不会带上 patch 里**新增**的文件。

**同步清单**（贴到 PR 描述或 issue 里，改完打勾）：

```
同步范围：[ ] master  [ ] mc1.16.5  [ ] mc1.15.2  [ ] 其它：______
```

> 只改**某些**分支也完全正常 —— 老版本冻结后本来就不该再动。判断标准是"这条线还需要这个改动吗"，
> 而不是"理论上应该一致"。

## 场景二：只有某个版本需要的改动

直接在那条分支上改，不需要同步：

```sh
git switch mc1.16.5
git switch -c mc1.16.5/fix-credits
# 只在这条线放这个文件（例：1.17+ 才用 texts/credits.json，1.16.5 用 texts/credits.txt）
```

该版本与其它版本路径不同时，照 [06-各版本路径变化对照](06-各版本路径变化对照.md) 查原版读哪个路径。

## 场景三：发一个版本

```sh
git switch mc1.16.5
git switch -c release/v8.8-mc1.16.5
# 1. 改 FPP/pack.mcmeta 的 version 字段 → "v8.8 for MC1.16.5"
# 2. 打包：Windows 上通常没有 zip 命令，用 Python 标准库
python - <<'PY'
import zipfile
from pathlib import Path
root, out = Path("FPP"), Path("FPP_v8.8_for_MC1.16.5.zip")
files = sorted(p for p in root.rglob("*") if p.is_file())
with zipfile.ZipFile(out, "w", zipfile.ZIP_DEFLATED) as z:
    for p in files:
        z.write(p, p.relative_to(root).as_posix())   # 根目录直接是 pack.mcmeta + assets/
print(out, len(files), "个文件")
PY
# 3. PR → 合并 → 打 tag 并发布
git switch mc1.16.5 && git pull
git tag v8.8-mc1.16.5 && git push origin v8.8-mc1.16.5
gh release create v8.8-mc1.16.5 FPP_v8.8_for_MC1.16.5.zip \
  --repo TecoStudio/Frozen_Pear_Pack --title "FPP冻梨子材质 v8.8 for MC1.16.5" --notes "..."
```

- tag 与资产命名规范见 [02-分支与命名](02-分支与命名.md)。
- **打 tag 前先核验**（见 [07-核验一条分支](07-核验一条分支.md)）：格式号对不对、路径有没有失效。
- 打包前删掉 `FPP/` 里混进的工作文件（`.DS_Store`、`.pdn`、`*.bak` 之类）。

## 场景四：回滚

```sh
# 只是本地改乱了
git restore FPP/

# 已经提交但还没推送
git reset --soft HEAD~1        # 保留改动，撤掉提交

# 已经推送（在主题分支上）
git revert <commit>            # 用 revert，别在共享分支上 force push

# 已经发布（tag + Release）
# 不要动/重命名已发布的 tag；发一个新版本号修掉，并在 Release notes 里说明
```

## 常用检查

```sh
git branch -r                                  # 有哪些远端分支
git show HEAD:FPP/pack.mcmeta                  # 当前分支的格式号 / 版本号
git log --oneline -5                           # 当前分支最近做了什么
git diff --stat mc1.16.5..master -- FPP        # 两条线之间差了多少文件
git status --short                             # 工作区是否干净
```
