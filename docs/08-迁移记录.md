# 08 · 迁移记录（2026-10-09 ～ 10-10）

这次把版本管理从**"单主干 + overlay + 构建脚本"**改成**"每个 MC 版本一条分支"**。本页记录
决策、动作与实测数据，避免以后重复考证。

## 为什么改

原方案（在 `feat/version-lines` 分支上，PR #16）用一份主体内容 + 每版本一个 overlay 目录 +
构建脚本产出 9 条线的 zip。放弃它的原因：

- 实测 9 条线的 zip **大小完全相同（都是 6.25 MB）** —— overlay 目录其实是空的，
  也就是说"分线"当时只体现在 `pack.mcmeta` 的格式号上，内容并没有真的分线。
- 主体 2715 个文件里 **1784 个是两个版本都读**（约 85% 的文件在各版本间完全相同），
  overlay 机制对这个现实没有收益。
- 每条线的 `pack.mcmeta`、路径、内容要能**彻底独立**，不依赖任何构建脚本。

分支制的代价（改一张通用贴图要重复 N 次、漏改一条线不报错）已知，用
[01-分支模型与纪律](01-分支模型与纪律.md) 的 patch 流程控制。

## 1.15.2 的内容来源：为什么用 tag 而不是 Release

一开始按"下载 v7.0 的 Release 迁出"来做，但**对账发现 Release 的 zip 是手工打包的衍生品，
不是源码**：

| 证据 | 结果 |
| --- | --- |
| Release `FPP_v7.0_for_MC1.15.zip`（2889355 B，2337 个文件） vs tag v7.0 源码树（2572 个文件） | Release **少 239 个文件**：5 个 `.mcmeta`、190 张逐帧 PNG、41 个 JSON、3 个无扩展名 |
| 196 张 PNG 两边内容不同 | 5 张**尺寸不同**（如 `diamond_ore.png`：tag 16×16 / Release 16×304）、5 张像素完全相同、25 张轻微色差、161 张明显不同 |
| `textures/block/diamond_ore.png.mcmeta` | 两边 **sha1 完全相同**（`6bf11560`） |
| `textures/item/minecart.png` | tag 与当前 master 都是 1872 B，Release 是 **253 B** 的压缩版 |
| 2 个 JSON 差异 | 只是 **CRLF vs LF**（171 B → 179 B），逐行内容相同 |
| 旧脚本 `dev-linux.sh` 原文 | "Please create pack.mcmeta into the dev.zip" —— 打包时手工塞进去的 |
| 与当前 master 对比 | 那 196 个文件里，tag 内容与 master 相同的占 169 个，Release 只有 2 个 |

结论：**tag v7.0 是那条线真正的源码**（逐帧 PNG + `.mcmeta` + 手写模型），
**Release 是打包产物**（把逐帧拼成动画条、有损压缩、JSON 转 CRLF、顺手丢了 239 个文件）。
所以分支放 tag 的树，`pack.mcmeta` 取自 Release（tag 里没有提交这个文件）。

> Release 原件仍可从 GitHub 取：`gh release download v7.0 -R TecoStudio/Frozen_Pear_Pack -p "*.zip"`。

## 迁移中顺手做的清理

- 剔除 tag 里被误提交的 **4 个 `.DS_Store`**（`.DS_Store`、`assets/.DS_Store`、
  `assets/minecraft/.DS_Store`、`assets/minecraft/textures/.DS_Store`）。
- `pack.mcmeta` 行尾 **CRLF → LF**（Release 里那份是 Windows 打的）。
- 撤销废弃方案留在**本机**的 git 配置：`core.hooksPath`（指向已不存在的 `.githooks`）、
  `branch.master.pushRemote=__no_push__`。服务端 `master` 的 PR 保护**未动**。
- 删除 `dist/` 下 174 MB 的构建产物（9 条线的 zip 与解包目录、246 MB jar 缓存）。
  > `master` 的 `.gitignore` 里**没有** `dist/`，所以当时 `git add -A` 一把梭把 174 MB 全暂存了。
  > 提交时用 `git add FPP` 这类精确路径，或考虑给 `.gitignore` 加一行。

## 核验基线（2026-10-10 实测，方法见 07）

| | `1.15.2` | `1.16.5`（= master 当前内容） |
| --- | --- | --- |
| 包内文件 | 2571（含 80 个 `.mcmeta`） | 2717（含 68 个 `.mcmeta`） |
| 该版本原版会读 | 1981 | 1980 |
| 该版本不读 | 588（旧路径残留 2 + 自建资源 586） | 735（旧路径残留 3 + 自建资源 732） |
| **挪了位置 / 老路径（要修）** | **0 / 0** | **0 / 0** |
| `.DS_Store` 残留 | 0 | 0 |

两条线都**没有需要修的失效路径**。

[04](04-开一条新版本分支.md) 与 [06](06-各版本路径变化对照.md) 里那张"各版本要处理多少"的表，
也是用同一版脚本（`--baseline 1.16.5`）重跑出来的，取代了迁移中途用较粗启发式得到的
`8 / 8 / 11 / 14 / 71 / 130 / 156 / 156`：口径变了（新口径同时算上"同名资源挪位置"和
"老路径改名/搬家"两类），所以数字不可混用。

> **一处自我纠正**：迁移过程中用较粗的启发式先得到过"1.15.2 有 5 个失效路径"的结论 ——
> 逐个查证后**没有一个是真失效**：其中 2 个是 `.png.mcmeta`（动画元数据本身不在原版 jar 里，
> 但它描述的贴图原版会读，属于误报），另外 3 个（`gui/container/villager.png`、
> `item/bamboo_stage0.png`、`misc/nausea.png`）是面向更新版本的白带，同样无害。
> 换成 07 里那版脚本（区分层级、`.mcmeta` 看基名、并检查"包里是否有能用的另一份"）后，
> 真实结论是 **0**。数字随方法变，所以 07 把判据与局限一并写清了。
