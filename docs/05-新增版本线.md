# 05 · 新增一条版本线

Minecraft 出了新大版本（或当前线有了最终补丁）时，加一条线就是加一条配置。

## 步骤

```sh
# 1) 在 FPP/build.json 的 lines 里加一项：
#    line / mc / packFormat / packFormatSource / packVersion / notes
#    格式号 ≥ 65（1.21.9 起，含 26.x）的线再加 formatShape: "range"
#    —— 核实格式号的方法见 03-版本线与格式号.md

# 2) 跑审计，看这条线有哪些文件其实不生效（原因见 04-路径兼容性审计.md）
python tools/audit.py --line mc26.4

# 3) 如果审计有结果、或这条线与主体本来就该不同，把差异文件放进差异层：
mkdir -p FPP/overlays/mc26.4/assets/minecraft/...
#    路径与资源包根目录一致；同名文件会覆盖主体。一个都没有就不用建这个目录。

# 4) 验证：组装"基线线 + 新线"，对比两个产物（两侧都已归一化行尾）
python tools/build.py --line mc1.16 --line mc26.4 --dev
diff -rq dist/FPP-mc1.16.5-v8.7 dist/FPP-mc26.4-v9.0   # 差异应只有 pack.mcmeta + 你有意放进 overlay 的文件

# 5) 全量构建 + 打包，确认 exit 0
python tools/build.py --all --zip
```

> ⚠️ 不要用 `diff -rq FPP/assets dist/...` 对比主体与产物：主体在 Windows 工作区里是 CRLF、
> 产物是归一化后的 LF，会刷出几百行假差异（本仓库实测 441 行）。
> 要么比两个构建产物，要么用 GNU diff 的 `--strip-trailing-cr`。

## 会自动跟上的东西

- **CI 矩阵由 `build.json` 生成**，不需要改 workflow：新增一条线就自动多一个构建任务，
  推 tag 时也自动进入 Release。
- `--list` / `--matrix` / Release 的产物命名都从这个 json 派生。

## 旧线不需要做任何事

既不用"切回去"，也不用 backport —— 主体没动，重新构建出来的内容和上次发布的完全一致。
（`git checkout` 只在复现已发布包时才用，见 [07-改动与-backport](07-改动与-backport.md)。）

## 别忘了

- `packFormat: null` 的线会**跳过构建**并提示，`--release` 下直接报错 ——
  这是防止"为了让构建跑通随便填个格式号"的保险。别绕过它。
- 新的 `pack_version`（包版本）按该线自己的节奏递增，各线独立，见
  [06-发布规范](06-发布规范.md)。
- `defaultLine` 决定不带 `--line` 时 `--dev` 组装哪条线；日常测的是当前版本时记得改。
