# 02 · 命令与产物

## 日常命令

| 目的 | 命令 |
| --- | --- |
| 看所有版本线 | `python tools/build.py --list` |
| 日常开发（默认线 mc1.21 解包到 dist/） | `python tools/build.py --dev` |
| 指定线组装（拖进游戏测试） | `python tools/build.py --line mc1.16 --dev` |
| 组装 + 打包 zip | `python tools/build.py --line mc1.21 --zip` |
| 全部线组装 + 打包 | `python tools/build.py --all --zip` |
| 发布前严格检查 | `python tools/build.py --all --zip --release` |
| 看哪条线 pack_format 还未知 | `python tools/build.py --unknown-lines` |
| 看某条线有哪些文件在新版本下其实不生效 | `python tools/audit.py --line mc26.3` |
| 审计全部线（会下载多个官方 jar） | `python tools/audit.py --all` |
| 装本地防误推钩子（clone 后跑一次） | `sh tools/setup-guards.sh` |

构建只需要 Python 3（纯标准库，无第三方依赖），**不需要 `zip` 命令**；
已实测环境：本机 Python 3.14 与 CI 的 `python3`（未在更老的 3.x 上实测过）。
`tools/audit.py` 需要联网（下载官方 client jar，缓存在 `dist/.jarcache/`）。

## 产物

- `dist/FPP-mc<MC目标>-v<包版本>/`（解包目录）与同名 `.zip`。
- zip 根目录是 `pack.mcmeta` + `assets/`（与游戏要求的资源包结构一致），
  不会把 `overlays/`、`build.json` 这类仓库文件打进去。
- `--release` 下若某条线的 `pack_format` 还是 `null`，脚本直接报错退出（exit 1），
  不会生成一个格式号错误的包。`packFormatSource: assumed` 的线只在日志里告警。

## 为什么产物是可校验的

**跨机器内容一致**：条目排序 + 固定时间戳 + 文本资源强制 LF。
实测"本地 Windows 构建"与"GitHub Actions 构建"的 zip **2717 个条目 CRC 全部相同**；
只有"压缩后的字节"会因 zlib 版本不同而略有差异（同机器重复构建则字节完全一致）。
所以一份发布包可以被重新构建出来核对内容。

具体三条规则：

1. **条目排序 + 固定时间戳**：`zipinfo` 里所有条目的时间是 `2020-01-01 00:00:00`，
   顺序按路径排序 —— 否则同一份内容每次打包的字节都不同。
2. **文本资源统一按 LF 写入**：`.json` / `.mcmeta` / `.txt` 在打包时归一化行尾。
   资源包内容不该随协作方 Windows 上的 `core.autocrlf` 设置而变 —— 否则同样的贴图
   只有行尾不同，本地测试的包和 CI 发布的包就不是同一个东西了。
3. **产物校验会拒绝残留 CRLF**：归一化漏掉的文件会直接判构建失败，而不是悄悄发布出去。

> 想核对"某条线到底跟主体差多少"，**要拿两个构建产物比**，别拿主体目录跟产物比：
> 主体在 Windows 工作区里是 CRLF、产物是归一化后的 LF，会刷出几百行假差异
> （本仓库实测 441 行）。可以 `python tools/build.py --line mc1.16 --line mc1.21 --dev`
> 后用 `diff -rq`，或给 GNU diff 加 `--strip-trailing-cr`。
