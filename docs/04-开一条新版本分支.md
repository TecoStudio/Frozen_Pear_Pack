# 04 · 开一条新版本分支

## 什么时候开

1. **Minecraft 出了新大版本** —— 按本方案，**最新版留在 `master`**。所以严格说新版本不需要
   新分支；需要开分支的是**被最新版取代的那条线**（"上一任最新"）。
2. **要把某个老版本正式当成一条线维护** —— 例如以后给 1.21.11、26.1.2 各留一条线。

## 从哪切

一律**从 `master` 切**（它是最新内容，最接近所有版本）：

```sh
git switch master && git pull
git switch -c 1.21.11
```

要注意 `master` 当前的**路径布局**是哪个年代的：

| master 的现状 | 给老版本开分支时 |
| --- | --- |
| 还是 1.16.5 时代的路径（**现在就是**） | 多数文件直接可用，只需按 [06](06-各版本路径变化对照.md) 修**该版本相对 1.16.5 变化的那些路径** |
| 已经切到最新版（26.x）的路径 | 要按 [06](06-各版本路径变化对照.md) **反向**把路径改回该版本读的样子 |

## 步骤

```sh
# 1) 确认该大版本的最终补丁号（一手来源：Mojang 官方清单）
curl -s https://launchermeta.mojang.com/mc/game/version_manifest_v2.json \
  | python -c "import json,sys; d=json.load(sys.stdin); print([v['id'] for v in d['versions'] if v['id'].startswith('1.21')][:12])"

# 2) 建分支，改 pack.mcmeta（格式号表见 05；1.21.9 起还要 min_format / max_format）
git switch -c 1.21.11
#    pack_format → 75
#    version     → "v9.0 for MC1.21.11"

# 3) 按 06 的对照表修该版本专属的路径

# 4) 核验（见 07）：确认"要处理"那一栏归零
python "$LOCALAPPDATA/Temp/fpp-verify/check_branch.py" 1.21.11 --baseline 1.16.5

# 5) 提交并推送（新分支不是 master，可以直接推；之后的改动一律走 PR）
git add FPP && git commit -m "feat(1.21.11): 迁出 1.21.11 版本线"
git push -u origin 1.21.11
```

> 别用 `git add -A`：`.gitignore` 里没有构建产物/临时目录，会把它们一起提交。

## 工作量预估（实测）

以**当前 `master` 的内容**（1.16.5 时代布局）为基准，对照各版本官方客户端实测
（方法见 [07](07-核验一条分支.md)）：

| 目标版本 | 原版会读 | **原版把同名资源挪了位置** | **老路径**（1.16.5 有、该版本没有） | 需要处理 |
| --- | --- | --- | --- | --- |
| 1.16.5 | 1980 | 0 | 0 | **0**（已建分支） |
| 1.17.1 | 2207 | 1 | 5 | **6** |
| 1.18.2 | 2208 | 1 | 5 | **6** |
| 1.19.4 | 2204 | 5 | 5 | **10** |
| 1.20.6 | 2182 | 8 | 24 | **32** |
| 1.21.11 | 2101 | 9 | 70 | **79** |
| 26.1.2 | 2035 | 41 | 94 | **135** |
| 26.2 | 2009 | 82 | 98 | **180** |
| 26.3 | 2007 | 82 | 99 | **181** |
| 1.15.2 | 1834 | 0 | 144 | **0**（见下） |

怎么读这张表：

- **"原版把同名资源挪了位置"** —— 一定失效，按 06 改路径。
- **"老路径"** —— 该路径在 1.16.5 原版里存在、目标版本已经没有。**只有当目标版本比 1.16.5 新时
  才需要处理**（那是原版搬走了你的画）。比 1.16.5 老时（例如 1.15.2 那一行的 144）
  属于"面向更新版本的白带"，**无害，不要动**。
- 表里没有算进去的还有"自建资源"（各版本 500～735 个）和"旧路径残留"：都是包自己加的变体/模型，
  或包里有能用的另一份，**无需处理**。
- 这是**一次性**工作量，不是持续开销 —— 分支建好、路径对齐之后就冻结了。

## 数字别当成手工活

"要处理 181 个"不是要你手工改 181 次 —— 绝大多数是**同一批路径的批量移动**（例：1.21.2 把
`textures/entity/*.png` 拆进 `entity/*/`，1.21.5+ 把实体贴图按变体重命名）。
先看 06 的对照表归类，再用 `git mv` + 少量内容替换批量处理。

## 顺序建议

1. **先把老线切出来**（1.16.5、1.15.2 已完成）：老版本内容已冻结，切出来就完事，代价最小。
2. **定期同步共享改动**（见 [03-日常流程](03-日常流程.md) 的同步清单）。
3. **最后再把 `master` 换成最新版布局**：master 一动，所有老分支的"反向路径差"就固定了，
   之后再动 master 也不会影响已冻结的老线。
