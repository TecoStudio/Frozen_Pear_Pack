# 06 · 发布规范

## 命名

- **包版本是每条线独立的**：`mc1.16` 停在 `v8.7`；新线都从 `v9.0` 起各自递增。
  所以"v9.0"在不同线下内容不同 —— 看文件名/标题里的 MC 目标即可区分。
- **tag**：`v<包版本>-mc<MC目标>`，例如 `v9.0-mc1.21.11`。
  推 tag 会触发 CI：构建**全部**线并把这些 zip 传进该 tag 的 Release。
- **zip 名**：`FPP-mc<MC目标>-v<包版本>.zip`（由脚本生成，别手改）。
- **`pack.mcmeta`**：`version` 字段为 `v<包版本> for MC<MC目标>`，如 `v9.0 for MC1.21.11`；
  由 `build.json` 生成，不要手写。
- 历史 tag `v7.0` … `v8.7` 全部属于 `mc1.16` 线，保持原样不动。

## 发版流程

```sh
python tools/build.py --all --zip --release   # 1) 严格检查 + 全量构建（格式号未知会直接报错）
git switch -c release/v9.0-mc26.3             # 2) 走分支 + PR（不要直接推 master）
# …PR 合并…
git tag v9.0-mc26.3 && git push origin v9.0-mc26.3   # 3) 推 tag 触发发版
```

CI 在 tag 上会重新从 tag 内容构建全部线（不下载 PR 的 artifact），再把 zip 传进 Release ——
**发布物与 PR 验证过的产物来自同一次构建逻辑**，不会出现"PR 绿了但发出来的是别的东西"。

> 📌 **release job 只在 tag 上运行，PR 里验证不到。** 第一次发版前留意这点：
> 推 tag 后要去看 Actions 是否成功，别假设它一定绿。

## 版本号怎么加

| 情况 | 怎么动 |
| --- | --- |
| 只改了贴图/文本，某条线要重发 | 该线的 `packVersion` 递增（例 9.0 → 9.1） |
| 新增一条版本线 | 给它一个起始 `packVersion`（新线从 `v9.0` 起） |
| 所有线都要重发 | 每条线的 `packVersion` 各自递增（它们不共享一个版本号） |

`packVersion` 是 `build.json` 里 `lines[].packVersion` 字段，改了它，`pack.mcmeta` 的
`version` 与 zip 文件名会一起变 —— 这也是"不要手写 pack.mcmeta"的原因之一。
