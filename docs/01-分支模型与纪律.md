# 01 · 分支模型与纪律

## 模型

```
master                 ← 最新 MC 版本（手动跟随，永远不带版本后缀）
   │
   ├─ 1.16.5            ← 冻结：内容止于 1.16 时代
   ├─ 1.15.2            ← 冻结：内容止于 1.15 时代
   └─ 1.21.11 / 26.x …  ← 以后按需加（见 04）
```

每条分支是一份**完整的资源包工作区**：`FPP/` 里就是包内容，`FPP/pack.mcmeta` 描述它属于哪个
MC 版本。分支之间**没有共享文件、没有构建脚本**，只有内容上的相似。

## 三条铁律

### 1. 永远不要在两条版本分支之间 merge / rebase

它们是各自演化的平行历史：`1.16.5` 用 1.16 的路径，`26.3` 用 26.3 的路径。
一次 merge 会把 A 版本的路径和 B 版本的文件混在一起 —— **不报错、不冲突**，
只是有人打开游戏发现某张贴图不生效（资源包是**被动覆盖**：路径不对就是静默失效）。
跨分支搬东西用下面两种方式，不要 merge。

### 2. 共享改动要在每条还在维护的分支上各做一次

这是分支制的主要代价。实测：各版本线之间 **85% 的文件内容完全相同**（2308 / 2715），
所以"改一张通用贴图"理论上要重复 N 次。少付代价的办法是**把一次改动做成 patch，逐分支 apply**：

```sh
# 1) 在改好的分支上导出（含提交信息）
git format-patch -1 --stdout > /tmp/fix-lantern.patch

# 2) 到每条要同步的分支上应用
git switch 1.16.5
git apply --index /tmp/fix-lantern.patch
git commit -m "fix: 灯笼动画（同步自 master）"
```

（`--index` 是必须的：`git apply` 单独用不会把 patch 里**新增**的文件放进暂存区。）

只想搬文件（贴图这类没有逻辑的改动）可以更直接：

```sh
git switch 1.16.5
git checkout master -- FPP/assets/minecraft/textures/block/lantern.png
git commit -m "fix: 灯笼动画（同步自 master）"
```

**别靠记忆**：改动落地的分支要打勾。清单模板在 [03-日常流程](03-日常流程.md)。

### 3. 每条分支的 `pack.mcmeta` 必须与该分支的 MC 版本匹配

格式号写错 = 游戏里直接显示"不兼容"，包根本不加载。对照表见
[05-pack.mcmeta-与格式号](05-pack.mcmeta-与格式号.md)。

## 其它纪律

- **不在 `master` 上直接提交**：服务端对 `master` 开了分支保护（要求走 PR，管理员同样受限）。
  工作一律 `git switch -c <主题>` → 提交 → PR。
- **`git add -A` 有坑**：`.gitignore` 里没有构建产物/临时目录，一把梭会把它们一起提交。
  用 `git add FPP`，或者只 add 你真正动过的路径。
- **`master` 只表示"最新"，不要给它加版本语义**：最新版本换代时，master 的内容被换成新版本，
  旧内容进它自己的分支（见 [04-开一条新版本分支](04-开一条新版本分支.md)）。

## 代价与收益（当初为什么这么定）

| | 单主干 + overlay | **每条版本一条分支（当前方案）** |
| --- | --- | --- |
| 改一张通用贴图 | 改 1 次，所有线自动生效 | **每条分支各 1 次** |
| 漏改一条线的后果 | 结构上不可能漏 | **不报错、不冲突，静默不一致** |
| 要动老版本 | 不需要切换，构建参数选线 | 需要切换分支 |
| 每条线的独立程度 | 共享内容强制同步 | 彻底独立（路径、`pack.mcmeta`、内容都能各写各的） |
| 依赖 | 依赖构建脚本 + overlay 目录约定 | **无脚本依赖**："这个分支就是那个版本的包" |
| 仓库里的重复 | 无 | 85% 的文件在分支间重复。git 按内容去重，`.git` 不会成倍增长；但**本地每多一份检出就多一份工作区**（约 7.6 MB/份） |

选择分支制的理由：每条线的 `pack.mcmeta`、路径与内容可以彻底独立，不依赖任何构建工具。
代价（重复劳动 + 静默漂移）已知，用第 2 条的 patch 流程控制。
